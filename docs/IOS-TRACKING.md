# Ride Garage 2.0: native iPhone ride recording

The iOS app packages the existing PWA with Capacitor 8 and a local Swift/Core Location plugin in `native/ride-recorder`. Core Location owns recording; a JavaScript timer or a running web view is not required while the screen is locked. The website remains a standalone PWA. Safari and an installed PWA cannot promise continuous locked-screen recording; use the native app for that feature.

## Build on a Mac

Prerequisites: Node.js 22, Xcode with its command-line tools and an iOS simulator runtime, Python 3 (for the standard-library plist editor), and CocoaPods 1.16.2. Capacitor 8 supports iOS 15 and later and requires Xcode 26 or later. Since April 28, 2026, App Store Connect uploads require Xcode 26 or later and the iOS 26 SDK or later; a successful simulator build alone does not satisfy submission requirements.

1. Check out this pull request's branch. In `capacitor.config.json`, choose an app ID controlled by your Apple Developer team before generating the project. The checked-in `com.ridegarage.app` is a starting value, not a claim to an existing App Store identifier.
2. Install dependencies and generate the native app:

   ```sh
   npm ci
   gem install cocoapods -v 1.16.2 --no-document
   npm run ios:init
   npm run ios:open
   ```

3. Open the generated `ios/App/App.xcworkspace`, select the **App** target, and set **Signing & Capabilities → Team** and a unique bundle identifier. Enable automatic signing. If you change the identifier after generation, update both Xcode and `capacitor.config.json`.
4. Connect and trust a physical iPhone, enable Developer Mode on the phone if required, select it as the run destination, and run **Product → Run**. A free development team may work for local testing; TestFlight and App Store distribution require Apple Developer Program membership.
5. After editing web or native sources, run `npm run ios:sync` and build again. Keep the workspace open if desired. This refreshes the packaged assets, local plugin and location plist settings.

`ios/` and `www/` are generated and ignored. The generation scripts preserve an existing iOS project and do not replace its signing choices. Commit permanent native behavior in the plugin or generation scripts so a fresh checkout reproduces it. The script explicitly selects CocoaPods because Capacitor 8 defaults to SPM. The plugin's Swift package is only for Foundation journal tests. Do not switch the app to SPM without adding the plugin's full Capacitor package support.

Capacitor, Playwright and all npm transitive dependencies are pinned in the committed `package-lock.json`, generated by npm on macOS and reviewed for this implementation. Use `npm ci` from a clean checkout. Native CI uploads `Podfile.lock` as build evidence; preserve the reviewed Pod lock with your generated signing project for release builds.

The build copies root-level runtime HTML, CSS, JavaScript, image and manifest files to `www/`; SQL, archives, docs, Git files and dependencies stay outside the bundle. It inserts the installed Capacitor core runtime before application scripts in packaged HTML. Capacitor injects the native bridge, and `cap sync` discovers and registers `RideRecorderPlugin`. The sync script verifies registration and CocoaPods linking. The native app uses bundled assets, and its web code skips PWA service-worker registration.

## How tracking and saving work

- **Start** asks for location access only after the rider chooses to record, while the app is in the foreground. Start and Resume require that same explicit action. Merely opening the app, signing in, viewing a map or restoring a backup does not start location tracking.
- **Pause** stops Core Location updates. **Resume** begins a new route segment. **Stop** ends background tracking before saving the completed ride. No points are collected while paused or after Stop.
- The native recorder requests navigation accuracy, keeps automatic location pauses disabled, and retains timestamped coordinates, horizontal accuracy, speed when available, and segment numbers. Every valid delivered fix is kept in the journal, including low-accuracy fixes. There is no every-Nth-point route reduction or endpoint-only line.
- The displayed route uses usable fixes with accuracy at most 60 metres. Pause/resume, location gaps over 30 seconds, and physically implausible jumps over 100 m/s split the geometry so it does not draw invented connections through missing sections. Actual recorded street turns remain in the point sequence; GPS is not road matching, and urban canyons, tunnels and weak reception can still cause missing or inaccurate turns. GPS distance and speed are estimates. Distance ignores small steps within twice the accuracy radius when both reported speeds are at most 0.5 m/s, to reduce stationary drift. All raw samples and drawable points remain. This can undercount genuine crawling below 1.8 km/h; movement with higher or unavailable speed still uses geometric distance.
- A versioned append-only journal lives at `Application Support/RideGarageRecorder/ride.jsonl`. Each point, control change and metadata update is synchronized to disk before the update is exposed. Files use protection that permits writes after the phone has first been unlocked following a reboot, so locking the screen does not block journal writes. The journal is excluded from automatic OS backup; completed rides remain eligible for the app's existing explicit backups.
- On a new process launch, a previously recording session becomes **interrupted**. Durable points are offered for recovery; the rider chooses Resume or Stop. Tracking never silently restarts. A stopped ride that could not be imported is retried. A malformed trailing journal record after an abrupt termination can be recovered through the preceding valid records. An intact but invalid interior record is preserved and reported rather than silently deleting history.
- Completed rides use the existing trip model and the same IndexedDB garage. Legacy `pts` contains the full usable coordinate sequence; `gps` retains native samples as `{latitude, longitude, timestamp, accuracy, speed, segment}`, and `segments` contains separate drawable route sections. `source: "ios-core-location"` and `nativeSessionId` identify the origin. The trip ID is stable as `native-<session id>`. Timestamps are Unix epoch milliseconds; accuracy is metres and raw speed is metres/second. Trip distance is kilometres, max speed is km/h, and `dur` excludes paused and interrupted time.
- Trip insertion and its odometer increment commit in one IndexedDB transaction. Retrying the same native session does not duplicate the trip or increment the odometer again. Only after the transaction completes does the web app acknowledge the stopped native journal for removal. If saving or acknowledgment fails, the journal stays available for retry. Existing garage writes are serialized with import to prevent an older edit from overwriting the saved trip.
- Pause and Stop invoke the native safety action without waiting for a ride-name update. A cosmetic metadata failure must not prevent the rider from stopping GPS.

The native recorder has no network upload path. Existing Supabase sign-in, community functions, account deletion, backups and private manual Cloud Garage Sync remain in place. Completed rides, including their GPS fields, are included in the existing garage backup and cloud snapshot flow. Cloud uploads still require the user's existing explicit action and remain subject to the existing roughly 8 MB size limit. Long rides retain raw GPS, legacy points and segments and can exceed that limit; use a local backup file or Show backup text when needed. No database migration, table deletion, automatic replacement or background cloud upload is introduced.

## Move an existing garage to the native app

The native app and Safari/PWA have separate storage sandboxes. Installing the app does not erase the PWA, but it also cannot automatically read the PWA's IndexedDB or existing sign-in session.

Download a backup from the PWA's Profile → Backup & restore and import it in the native app, or sign in to the same Supabase account and use the existing private Cloud Garage Sync merge. Keep a backup before transferring. WebView blob downloads may not save a file on every iOS version; Show backup text and copying the JSON provides a fallback. Sign in again inside the native app; existing email/password sign-in uses the same Supabase project and public configuration. Email confirmation and password-recovery links may open the configured website. No native OAuth/deep-link callback has been added, so any future native redirect flow must be configured and tested separately.

## Language

Use the **Language / Idioma** selector above the main screens to choose **English** or **Español (México)**. The Cloud Garage Sync page has the same selector. The choice is remembered on this device, separately from garage records and backups. Without a saved choice, a Spanish device/browser uses Mexican Spanish; other supported defaults use English. Recorded names, notes, posts, coordinates, country/category values and existing backups are never translated.

Changing language redraws interface labels and dates without restarting, pausing or stopping GPS. Unsaved form text and selected files are preserved. The web PWA includes both languages in its offline shell.

The generated native app bundles English and Spanish `InfoPlist.strings` resources. Apple chooses the system location dialog language from the iOS app/system language, independently of the in-app selector. To test both dialogs, use **iPhone Settings → Ride Garage → Language**, if available, or the device language. The configuration script uses the `xcodeproj` Ruby gem installed with CocoaPods; run it in that same Ruby environment.

Physical language checks: verify a fresh Spanish iPhone receives the Spanish location purpose text; switch the app between English and Spanish during an active ride; verify no GPS restart or loss of entered ride name; relaunch and verify the selection persists. Existing legal/support documents and external service diagnostics may use their original language.

## Apple location permissions and limits

The generated Info.plist contains:

- `NSLocationWhenInUseUsageDescription`, explaining route recording after Start, continuation with a locked screen, and how Pause/Stop ends updates.
- `UIBackgroundModes` containing `location`, shown in Xcode as **Background Modes → Location updates**.

The recorder uses `requestWhenInUseAuthorization` and foreground-started continuous location updates with `allowsBackgroundLocationUpdates`. It displays Apple's background location indicator. This session-based design does not request **Always** access and does not add the Always purpose string. Always permission would not guarantee survival after a force quit and is unnecessary for the foreground-started session supported here.

Choose **Allow While Using App** and enable **Precise Location** for useful street-level routes. **Allow Once** is temporary; future recording may prompt again. With denied/revoked permission, disabled system Location Services or reduced accuracy, recording is blocked or interrupted. The app reports the problem and stops updates on fatal permission/storage failures; change location access in iPhone Settings when needed.

High-accuracy GPS consumes battery. Screen lock saves display power, but GPS remains active throughout a recording. Battery condition, Low Power Mode, thermal pressure, weak reception and iOS scheduling can reduce availability or accuracy. Keep the phone charged for long rides and test on the supported iPhone/iOS combinations.

No iOS app can guarantee uninterrupted recording after a user force quit, OS termination, reboot, power loss, permission revocation or storage failure. Already synchronized data is recoverable where intact, but locations while the process is terminated cannot be reconstructed. Reopen the app and explicitly Resume; a recovery gap remains separate on the route. This implementation does not claim automatic background relaunch or add unrelated background fetch/processing modes.

## Checks before release

Run the browser tests against disposable local data:

```sh
npm ci
npx playwright install chromium webkit
npm run test:web
npm run test:journal
npm run ios:init
xcodebuild -workspace ios/App/App.xcworkspace -scheme App -configuration Debug -sdk iphonesimulator -destination 'generic/platform=iOS Simulator' CODE_SIGNING_ALLOWED=NO build
```

The browser workflow checks Chromium and WebKit, including native bridge mocks. `test:journal` requires Swift on macOS; native CI runs it and compiles the generated workspace on macOS without signing. Browser mocks and simulator compilation do not prove real-device background operation. Perform and record the following on a physical iPhone before shipping:

| Scenario | Expected result |
| --- | --- |
| Fresh install; browse all tabs without Start | No location permission prompt and no location recording. Existing web functionality works. |
| Start; grant While Using App and Precise Location | Recording begins after consent; samples have increasing timestamps and accuracy. |
| Record a route with several corners; lock for at least 15 minutes | Location indicator remains visible as appropriate; points continue across the locked interval; corners appear on the route after unlock. Test as a passenger or on a suitable walking route. |
| Pause; lock and move; unlock | No new points during pause; elapsed recording time/distance excludes the pause. |
| Resume; lock and record another section | New samples arrive in a new segment; no line or distance bridges the pause. |
| Stop while online and while offline | Background indicator/updates stop; one trip and one odometer increment are saved; reopen shows the same trip. |
| Airplane mode/offline, including a locked interval | Recording and local saving work without Supabase; maps may lack uncached tiles. Upload remains an explicit later action. |
| Navigate between tabs or reload the web view during recording | Native recording continues; the authoritative native session refreshes the controls on return. |
| Force quit or terminate during recording; relaunch | Durable session is shown as interrupted; no silent tracking; Resume/Stop works and the missing interval stays separate. |
| Terminate after Stop or simulate an IndexedDB/acknowledgment error | Pending stopped journal can be imported on retry; the stable ID prevents duplicate rides and odometer changes. |
| Deny/revoke access; disable Precise Location; disable Location Services | Clear status and a recoverable session where possible; no silent claim of a complete route. No updates after a fatal stop. |
| Stationary hold outdoors for 5 minutes, followed by slow movement and real street turns | Raw samples remain available; check estimated distance/odometer for GPS drift and compare with a known route. |
| Low Power Mode, battery pressure, poor GPS, full storage | Behavior and any gaps/errors are visible; existing trips are preserved and the app does not silently acknowledge a failed save. |
| Existing backup restore and manual cloud upload/merge | Existing records survive; completed native GPS metadata survives a backup round trip; Supabase sign-in and community still work. |

Use a spare test garage/account for failure injection. Inspect saved `gps` timestamps and `segment` values in a backup, not just the map's visual appearance. For locked-screen testing, use a physical device disconnected from the debugger as well as a development run, and repeat with a signed Release/TestFlight build.

## App Store and privacy

Before distribution, configure a real signing team/bundle ID, version/build number, 1024px App Store icon and required app icons, screenshots, support contact, privacy-policy URL and App Store Connect record. Generated Capacitor placeholder assets need replacement before release. Use TestFlight to validate a signed build on supported physical devices. Keep the Location updates capability and precise, localized purpose text.

Explain the foreground Start action, recording controls and locked-screen route purpose in App Review notes; provide reviewers a route to exercise the feature without requiring unavailable hardware or a private account. Background location must be used only for the stated active-ride feature. The shipped app must satisfy Apple's minimum-functionality and other review rules.

Review the app's bundled privacy manifests, including Capacitor's manifest and all added SDKs, and declare any required-reason API use accurately. The recorder itself uses no UserDefaults, file timestamp, uptime or disk-space APIs that require a reason declaration. Location permission strings are separate from privacy manifests. Keep the public privacy policy and App Store privacy answers consistent with local route storage and any rider-initiated cloud upload of precise location, account identifiers and other garage data. Core Location permission is not consent to publish routes. Complete Apple's encryption/export-compliance questions for the shipped app and its HTTPS services. Recheck the current Apple SDK and review requirements at submission time.
